1.1 — Contexte de la mission

Dans le cadre d'un partenariat entre Safran et l'ENSTA via la Junior Entreprise, cette mission de 2 Journées d'Étude Homme (JEH) s'est fixé pour objectif d'explorer la capacité de l'intelligence artificielle générative à produire automatiquement du code SysML v2 complet et des diagrammes d'architecture à partir de descriptions en langage naturel.

SysML v2 (Systems Modeling Language version 2) est la norme de facto pour la modélisation de systèmes complexes dans l'industrie aéronautique et de défense. Sa maîtrise requiert une expertise spécialisée et un investissement en temps considérable. L'émergence des grands modèles de langage (LLM) ouvre une voie nouvelle : déléguer la production de la syntaxe formelle à une IA, tout en conservant à l'ingénieur système la maîtrise des choix d'architecture.

1.2 — Objectifs de la mission

① Prompts de génération SysML v2

Formuler, tester et affiner les instructions envoyées à l'IA pour qu'elle produise du code SysML v2 syntaxiquement valide et sémantiquement fidèle à la description fournie, niveau par niveau selon l'approche MBSE.

② Prompts de visualisation des diagrammes

Explorer comment l'IA peut guider la génération de représentations graphiques (use case, BDD, IBD…) et comment Eclipse SysON peut servir de visualisateur open-source de référence.

Ces livrables sont directement réutilisables par les ingénieurs Safran comme base de travail pour de futurs projets de modélisation assistée par IA. L'approche repose sur Google Gemini 2.5 Flash, un RAG de 337 chunks SysML v2 officiels, et une progression en 4 niveaux MBSE.

1.4 — Choix du LLM pour un pipeline SysML v2

Les différentes variantes au sein d'une même famille de modèles présentent des profils très distincts. Pour un pipeline SysML v2, le choix se fait selon trois critères : qualité du code structuré généré, coût et latence, et capacité à suivre des contraintes strictes (schéma IR JSON, RAG, règles de fidélité).

Famille Variante Profil typique Usage recommandé (SysML v2)
Claude Haiku Plus rapide / moins coûteux · extraction et tâches simples bien cadrées Étape NL → IR JSON sur cas simples, batch de normalisation
Sonnet ★ Bon compromis qualité / coût / vitesse · très solide pour génération de code structuré Candidat principal pour IR → SysML v2
Opus Plus capable (raisonnement complexe) · plus cher / plus lent Cas ambigus, validations complexes, prompts longs
OpenAI GPT GPT-5.2 Flagship généraliste / coding-agentic · bon pour pipelines outillées Chaîne complète IR + RAG + validation + réparation automatique
GPT-5 mini ★ Plus rapide / moins cher · bon pour tâches définies et prompts précis Extraction IR, classification, normalisation sémantique
GPT-5 nano Très rapide / coût minimal · micro-tâches et pré/post-traitements Checks simples, filtres, sanitation, scoring heuristique
GPT-5.2 Codex Optimisé coding / agentic longue-horizon Pipeline avec outils + boucle de correction itérative
Gemini Pro Capacité plus élevée · tâches complexes / contexte riche Génération SysML v2 complète + raisonnement sur cas difficiles
Flash ★ (utilisé) Plus rapide / efficace · faible latence Étapes de pipeline / RAG orchestration / IR — modèle retenu pour cette mission

Détail des 4 niveaux MBSE

Le niveau opérationnel décrit le système vu de l'extérieur, comme une boîte noire. Il répond aux questions : Qui interagit avec le système ? Dans quel but ? Dans quels contextes ?

  • Stakeholders : acteurs humains (opérateurs, maintenanciers) et systèmes techniques qui interagissent activement (A/C Avionics, EECS, système pneumatique avion).
  • Systèmes externes : entités à la frontière du périmètre (ex. : SOV — Shut-Off Valve comme frontière physique passive).
  • Use cases : fonctions de service rendues par le système à ses stakeholders (ex. : PressuriserEtTempererLaCabine, DegivrerLaNacelle, DiagnostiquerLEtat).
  • Scénarios opérationnels : séquences d'interactions décrivant le déroulement des use cases.
  • Exigences de haut niveau : contraintes mesurables liant le système à son environnement.
Diagrammes associés : diagramme de contexte, diagramme de cas d'utilisation.

Le niveau fonctionnel ouvre la boîte noire et décrit les fonctions internes qui permettent de réaliser les use cases opérationnels. Il reste indépendant de toute technologie.

  • Fonctions avec leurs sous-fonctions hiérarchiques (ex. : GérerLePrélèvement → PréléverAirIP, PréléverAirHP).
  • Flux fonctionnels typés : chaque échange est catégorisé — pneumatique, information, électrique, thermique, mécanique.
  • Modes opératoires : configuration des fonctions actives selon l'état du système (OFF, Stand-by, Running).
Règle de traçabilité : chaque use case du niveau opérationnel doit être couvert par au moins une fonction.
Diagrammes associés : arborescence fonctionnelle (FBS), diagramme de comportement fonctionnel.

Le niveau logique décompose le système en composants logiques indépendants de la technologie. Il décrit l'architecture de solution sans descendre aux choix d'équipements.

  • Parts (composants logiques) avec leurs ports d'interface.
  • Connexions entre ports (ex. : FluxAirHautePression : GestionnairePrelevement.sortieAir → RégulationPression.entreeAir).
  • Allocation des exigences : chaque exigence est allouée au composant logique responsable.
Règle de cohérence : toute connexion doit lier deux composants définis dans parts.
Diagrammes associés : Block Definition Diagram (BDD), Internal Block Diagram (IBD).

Le niveau technique instancie l'architecture logique avec des composants physiques réels et des technologies concrètes.

  • Composants physiques nommés avec leur désignation d'équipement (ex. : HPV, PRV, Exchanger_ACAC, ElectronicBASControl).
  • Connexions physiques (canalisations, câblages, interfaces mécaniques).
  • Choix technologiques documentés (matériaux, normes, protocoles).
Règle : l'IA ne propose jamais de marque ou modèle non mentionné par l'utilisateur.

Catégorie 1 — Prompts de génération du modèle SysML v2

Un prompt efficace pour générer du SysML v2 est composé de 6 éléments : ① Rôle, ② Contexte MBSE, ③ Règles de fidélité, ④ Format de sortie JSON, ⑤ Exemple de structure annoté, ⑥ Exemples RAG injectés dynamiquement. Cette architecture a été validée empiriquement sur le BAS Silvercrest : les variantes qui omettent l'un de ces composants produisent systématiquement des régressions mesurables.
① Rôle → ② Contexte MBSE → ③ Règles fidélité → ④ Schéma JSON → ⑤ Exemple → ⑥ RAG

Objectif : extraire de la description utilisateur les acteurs, les systèmes externes, les cas d'utilisation, les scénarios opérationnels et les exigences mesurables. Fichier source : backend/prompts/operational_prompt.py — fonction build_operational_json_prompt().

P1/P5 Distinction stakeholder / système externe :

Un stakeholder est soit une PERSONNE/ORGANISATION, soit un SYSTÈME TECHNIQUE qui est ACTEUR dans un cas d'utilisation (qui initie des interactions, envoie des commandes, ou reçoit activement des services). Exemples : un calculateur moteur (EECS) qui envoie des consignes EST un stakeholder de type "system". En revanche, une vanne d'isolement physique (frontière passive) n'est PAS un stakeholder mais un external_system. Le champ "stakeholders" ne doit JAMAIS être vide si des entités interagissent activement.

P2 Exigences = contraintes mesurables uniquement :

Ne génère des requirements QUE pour des contraintes explicitement chiffrées ou mesurables (temps de réponse, disponibilité, capacité, température, etc.). Un comportement fonctionnel décrit (ex: "la vanne s'ouvre") N'EST PAS une exigence. C'est un comportement normal du système capturé dans les use cases, pas dans les exigences.

P8 Décomposition des use cases par destination :

Si un cas d'utilisation est de type "Fournir/Envoyer X à Y" et que la description mentionne PLUSIEURS destinations distinctes, décompose-le en sous-use cases séparés par destination. Exemple : "Le système fournit de l'air régulé à l'avion pour pressuriser la cabine, dégivrer les ailes et pressuriser les réservoirs" → génère 3 use cases distincts.

Le système BAS (Bleed Air System) est un système de prélèvement et de conditionnement d'air intégré au moteur Silvercrest. Il est intercalé entre la turbomachine et l'avion.

Le système interagit avec les entités externes suivantes :
- L'avionique de l'avion (A/C Avionics), qui fournit l'énergie électrique, envoie les consignes de pression et température, envoie les commandes de dégivrage, et reçoit les données d'état du système.
- La turbomachine (cœur du moteur), qui est la source d'air chaud à haute pression.
- Le conduit de soufflante (Fan by-pass duct), qui est la source d'air froid ambiant.
- La nacelle, qui reçoit l'air chaud pour le dégivrage et évacue l'air de refroidissement.
- Le système pneumatique de l'avion (A/C Pneumatic System), qui reçoit l'air conditionné et régulé en pression et température.
- La vanne d'isolement de l'avion (SOV - Shut-Off Valve), qui est la frontière physique en sortie du BAS.

Le système réalise quatre fonctions de service :
1. Envoyer de l'air régulé en pression et température à l'avion.
2. Envoyer de l'air chaud à la nacelle pour le dégivrage.
3. Déterminer l'état du système par mesures physiques et auto-diagnostic.
4. Communiquer les consignes et statuts avec l'avionique.

Le système possède trois modes de fonctionnement :
- OFF : Le système n'est pas alimenté, aucune vanne n'est active.
- Stand-by : Le système est alimenté et communique son état, mais les commandes de flux d'air ne sont pas activées.
- Running : Le système régule activement la pression et la température.

Sous-système de Prélèvement d'air :
- IP Port (Intermediate Pressure) : prélèvement primaire d'air chaud depuis la turbomachine.
- HP Port (High Pressure) : prélèvement secondaire d'air chaud depuis la turbomachine.
- HPV (High Pressure Valve) : vanne qui contrôle l'ouverture du port HP.
- IPCV (Intermediate Pressure Check Valve) : clapet anti-retour.

Sous-système de Dégivrage Nacelle :
- NAIV (Nacelle Anti-Ice Valve) : vanne d'arrêt.
- NAI press. sensor : capteur de pression.
- Nacelle anti-ice port : interface de sortie.

Sous-système de Conditionnement :
- PRV (Pressure Regulating Valve), Exchanger ACAC, FAV (Fan Air Valve), Filter.

Sous-système de Mesure : Bleed press. sensor, Bleed temp. sensor.

Sous-système Contrôle-Commande :
- Electronic BAS Control (EEC) : calculateur envoyant commandes aux vannes HPV, PRV, FAV, NAIV.

Limitation 1 — Condensation fonctionnel/technique en V2
Le code SysML v2 généré est −70 % plus court au niveau fonctionnel et −92 % plus court au niveau technique. Cause : la description enrichie (155 lignes) consomme plus de tokens dans le contexte, laissant moins de budget pour la génération. Le paramètre max_tokens insuffisant conduit le LLM à produire des versions condensées. Solution : régénérer les niveaux fonctionnel et technique en session dédiée avec max_tokens=65 536.
Limitation 2 — Le diagramme de cycle de vie reste hors de portée
Le Lifecycle Diagram passe de 0 % (V1) à 0 % (V2) malgré l'ajout de la section cycle de vie. Le pipeline génère 4 niveaux MBSE centrés sur l'architecture fonctionnelle en opération. Le cycle de vie est transverse — il nécessiterait un 5ème niveau dédié dans le pipeline ou un prompt de diagramme d'état spécialisé.
Limitation 3 — Description spontanée toujours incomplète
70 % des écarts proviennent d'informations absentes de la description initiale. C'est une constante : un ingénieur système ne pense pas spontanément à décrire le cycle de vie, les opérateurs de maintenance ou la décomposition fine des use cases. Solution : les 5 prompts d'élicitation (section 4.2) permettent d'atteindre ~94 % de couverture en dialoguant avec l'utilisateur avant la génération.

Conclusions et recommandations

✅ Conclusions
  • ✅
    Les prompts structurés en 6 composants sont efficaces pour générer du code SysML v2 syntaxiquement valide sur des systèmes complexes de 15 composants et 4 niveaux MBSE.
  • ✅
    Le pipeline NL → JSON → SysML v2 offre une traçabilité complète et un point d'inspection intermédiaire : l'ingénieur valide le JSON avant la génération du code.
  • ✅
    L'approche itérative améliore mesurablemet les résultats. Les 8 corrections P1–P8 : UC Services +21 pts · UC Maintenance 0→43 % · Acteurs 3→5.
  • ✅
    La répartition des causes est claire : 70 % description · 27 % prompt · 3 % IA. La description est le levier principal, pas le raffinement des prompts.
→ Recommandations opérationnelles
  1. Privilégier les descriptions structurées et détaillées — style formel en sections (entités, fonctions, modes, architecture, exigences) · vocabulaire technique précis.
  2. Utiliser les 5 prompts d'élicitation avant la génération — flux, acteurs humains, maintenance, cycle de vie, décomposition — pour passer de ~42 % à ~94 % de couverture.
  3. Procéder par itérations courtes — générer le niveau opérationnel → vérifier les use cases dans SysON → compléter la description → passer au niveau suivant.
  4. Envisager un niveau "Cycle de vie" dédié dans le pipeline pour les projets où la maintenabilité et la certification sont contractuellement importantes.
  5. Garder un rôle d'architecte actif — l'outil traduit, il ne conçoit pas. Les choix d'architecture restent sous la responsabilité de l'ingénieur système.
